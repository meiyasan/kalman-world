Detailed Description

The registry of compiled models — how a C++ model becomes nameable.

libKalman ships no physics: a model is written downstream, in an application, a ROOT+ analysis or a plugin. The factory is what lets such a model be found by name by something that did not compile it — the Python package's catalogue, the MCP server, a ROOT macro — and constructed without the caller knowing its type.

A model registers itself once, at static-initialisation time:

class ConstantVelocity : public Kalman::Models::Linear { ... };
KALMAN_REGISTER_MODEL(ConstantVelocity, "constant-velocity");

std::unique_ptr<Kalman::Model> model = factory.Create("constant-velocity");

Models compiled into a shared library register the same way; LoadPlugin() dlopens the library and the static registrars run. That is the one code path by which a model written for ROOT+ — linking ROOT, RooFit or anything else — can reach the Python side: ROOT stays inside the plugin, and the framework never sees it.

Every failure is loud: registering a name twice, creating an unknown name or loading a library that does not exist throws with a message that names what was expected. There is no silent fallback anywhere in this class.

Warning
Loading a plugin executes code. Nothing in this class decides which libraries may be loaded — that policy belongs to the caller (the Python API keeps an allow-list of directories), not to the registry.
