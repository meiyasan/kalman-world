The Kalman contract

One vocabulary for the whole library, in C++ and in Python. This page is the reference: every public term, what it means, who owns it, and how the words of the ensemble filter and of track finding map onto it.

The Status columns say where the code stands: in place, or the step of the consolidation that brings it. Until a step lands, the code still carries the older name given in the last table.

The rules

  1. The contract speaks control engineering: f, h, predict, update, prior, posterior, measurement, initial state. That is what a model, the base engine and the filter expose.
  2. **f and h take one state or many.** There is no second pair of names for the many-states form. step and sense are their readable aliases; a model's author writes f and h only.
  3. A community's words live inside its filter. The ensemble filter keeps forecast, project, analysis, localization, inflation, members. Track finding keeps hit, layer, seed, hole, candidate, chi-square gate. Each such name is implemented by the generic method and carries a comment that names it.
  4. No speed is lost. A path that is batched or multi-threaded stays so, and is measured before and after a change.
  5. Same names in C++ and Python (CamelCase and snake_case). C++ is the implementation; Python parses arguments and wraps.
  6. A replaced public name is removed, not kept as an alias.

The model: what the system is

f moves the state one step, h says what the sensors read:

x(k+1) = f(x(k), u(k), t(k)) + w(k) w: process noise, covariance Q
z(k) = h(x(k), t(k)) + v(k) v: measurement noise, covariance R

x is the state, u the command applied, t the time of the step (absolute time, in the model's unit; the step length is never passed, a model derives it from its sample rate), z the measurement.

The three vocabularies

The same mathematics was named three times: by control engineering (Kalman, 1960), by weather forecasting, where the ensemble filter comes from (Evensen, 1994), and by particle physics, where track finding comes from. The contract uses the first. The other two stay inside their own filter.

Two words that mislead:

  • Localization in the ensemble filter is not about finding a position. It is a table of weights between 0 and 1, computed from distances, laid over the sampled covariance so that an observation only corrects what is near it. On a model it is called covariance_mask.
  • CKF here is the combinatorial Kalman filter of particle physics. In control engineering the same letters mean the cubature Kalman filter.

What only one engine needs from a model is a small mixin beside the contract: covariance_mask for the ensemble filter, radii and seed_state for track finding. These are the classes KalmanEnsembleModel and KalmanDetectorModel (Engines::EnsembleModel and Tracking::Detector in C++), which a model inherits beside the contract; the engine checks for the class.

Names being replaced

Already gone: model.forecast(X) and model.observe(X), now f and h given many states; model.initial_ensemble(N), now model.initial_state(samples=N); initial_state_vector, initial_state_covariance and the get_initial_state variants, now initial_state(x0, P0); model.localization(), now model.covariance_mask(); sensor_id, the first argument of a model, now sensor (a name, a KalmanSensor, or a list); the label list (add_sensor("X"), remove_sensor, clear_sensors, sensor(i)), now a sensor's labels. CompositeKalmanModel and its readouts FUSED / INDEPENDENT, now compose (Composite) with SUMMED / STACKED. InteractiveKalmanFilter (IKF) and Filters::IKF, now route (Router, Models::Router) on the interacting engine; its mu_log and nis_log are mode_probabilities and nis_history; the storm models' ikf_bank is regime_bank. "Twin" now only means the twin experiment of the weather application: the C++ class that stands for a Python model is its counterpart (NativeCounterpart, was NativeTwin; KALMAN_NATIVE_COUNTERPARTS, was KALMAN_NATIVE_TWINS).
