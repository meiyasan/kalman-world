libKalman — the C++ library

libKalman is the framework core in C++: a standalone library with no required dependency. Not ROOT, not Eigen, not Torch — a C++20 compiler and nothing else.

It is a port, not a binding. It does not wrap the Python package, does not link CPython, and is not generated from anything. The two implementations share a design — Model / Engine / Filter — and meet at exactly one, deliberate seam: models. A model compiled here registers itself with Kalman::Factory, and the Python package reaches it through the C API (Kalman/CAPI.h) as an ordinary KalmanModel — catalogue, API, MCP server and notebooks included. The last section of this page has the measurements that put the seam there and not at every filter step.

The dependency direction matters and runs one way:

root-plus (Signal component) ──links──▶ libKalman ──▶ (nothing required)

The artefact is libKalman.so — it names the framework, and cannot be mistaken for root-plus' own much smaller ROOT::IOPlus::TKalmanFilter. Headers stay under Kalman/ and the namespace stays Kalman.

A ROOT or ROOT+ component links libKalman; libKalman never reaches for ROOT. That is what lets it also be linked by a plain C++ analysis, an embedded target, or a GPU pipeline that has never heard of CERN.

src/ follows the same tree wherever there is an implementation to hold; the purely declarative headers (Abstract/, Models/, Filters/) have no .cc because there is nothing to compile, not because they are missing.

Not ported yet, and deliberately absent rather than stubbed: the learned controllers (NeuralKalmanController, NeuralAdaptiveQRKalmanController — their training is Torch, and what would cross is a trained policy through the ONNX seam, as for the routers), the reserved integrator/solver kinds (ImplicitEuler, FiniteVolume, FiniteElement — Make() throws for them, as resolve_* does in Python). Of the routers, training stays Python-only by design — routers/nn/ is Torch, and the optimiser and data loaders belong there. What crosses is the finished policy, via NN::Torch or NN::Onnx. Every EngineKind now has a C++ engine; an integer that is not a kind still raises rather than silently becoming a linear step.

Roles and utilities

A role is something a user chooses or writes; it has a base class, a Kind constant and a directory. A utility is arithmetic nobody chooses between.

What it answers Where
Integrator (role) how do I advance in time? Kalman/Integrators/
Solver (role) how do I handle space, for a field? Kalman/Solvers/
Differentiator (role) where do Jacobians come from? Kalman/Differentiators/
Algebra (utilities) Cholesky, solves, eigenvalues, exp(A), the Riccati equation Kalman/Algebra/

"Solver" here always means a field solver. The linear solver of the framework is Cholesky, in Kalman/Algebra/Cholesky.h: a covariance is symmetric positive-definite, so nothing needs LU. Kalman::Utils keeps the Kalman arithmetic (missing channels, the Joseph update, sigma-point sums) and still exports the algebra names, so existing code compiles unchanged.

The three roles

Role Question Class
Model WHAT is the system? Kalman::Model → Models::Linear, Models::Extended
Engine (alias Estimator) HOW to infer? Kalman::Engine → Engines::Linear, Engines::Extended, Engines::Unscented, Engines::Particle, Engines::Ensemble, Engines::Combinatorial
Filter WHEN does it run? Kalman::Filter → Filters::KF, Filters::EKF, Filters::UKF, Filters::PF, Filters::EnKF; Filters::IKF, Filters::CKF

Solver HOW, in space? Kalman::Solver → Solvers::Spectral, Solvers::FiniteDifference

Dependencies point one way only: Filter → Engine → Model.

An ODE model overrides Model::Derivative() and calls UseContinuousDynamics(); the default f() then advances the derivative one sample with the model's declared integrator (RK4 unless SetIntegrator() says otherwise, in Substeps() pieces), exactly as a DYNAMICS = CONTINUOUS model does in Python. A field solver composes an integrator the same way and marches a Kalman::Field through the integrator's Butcher tableau — one RungeKuttaStep template serves a Kalman::Vector and a spectral field alike.

A controller closes the loop: Filter::Forward(zk, controller) calls it once per step with the belief, the time and the last innovation, and feeds the command to the prediction — KalmanFilter.forward(zk, uk=controller) in Python. The cost it logs is charged against Model::ClipControl(u), what the actuator delivers, not the raw ask; MPPI's rollouts clip the same way, so a planner sees the limit it will hit. LQR solves the Riccati equation with Algebra::SolveDARE (the recursion, then Newton steps on a Stein equation summed by doubling: no scipy and no factorisation beyond Cholesky); the two adapters scale R (a gain boost when the NIS says the filter is surprised) and Q (from the empirical innovation covariance). The Python controllers and the rule-based routers forward to these classes; see C++ models from Python.

Track finding is a different shape of problem — an event of many hits per layer in, a set of tracks out — so Engines::Combinatorial adds Find() and SmoothTracks() over a whole event on top of the inherited Extended step, and Filters::CKF is its leaf rather than a Kalman::Filter. A trackable model implements Kalman::Tracking::Detector (Radii(), SeedState()) next to Kalman::Model; tests/cxx/DriftChamber.h is the fixture, the counterpart of apps/tracking/driftchamber.py. On an identical event the two searches find the same tracks hit for hit — the test records one such case.

Engine::Predict / Update / Smooth have a shared Gaussian implementation that the Jacobian engines use as is; the sigma-point engine overrides the first two, and the two sample-set engines (particle cloud, ensemble) override all three — they are stateful, reseeded by Engine::Reset() when a run starts, and declare HasSmoother() == false, so Filter::Backward() refuses instead of pretending an RTS pass exists over a cloud.

Plus Kalman::Record (one pass, with its covariance band), Kalman::Diagnostics (NIS / NEES / gains, asked about a run rather than being steps of one), Kalman::Sampler (truth and measurements drawn from a model), Kalman::Matrix / Kalman::Vector (the small dense types), and Kalman::Utils (Cholesky with a pseudo-inverse fallback, NaN channel masking, central-difference Jacobians, the Joseph form).

No physics. A pendulum, a drift chamber, a suspension or a power grid is an application: it subclasses Models::Linear or Models::Extended and lives where the domain knowledge lives — the same split as modules/framework/ versus modules/apps/ on the Python side. libKalman ships the contract those applications are written against and nothing more. The models in tests/cxx/Fixtures.h are test fixtures, not a catalogue.

No plotting and no I/O. Record::Series() / Sigma() hand back the arrays a plot needs; turning them into a TGraphErrors, a matplotlib axis or a CSV is the integrator's job, because that is where the plotting dependency belongs.

The AI runtimes are looked for by libKalmanLearn only. libKalman never links one, whatever is installed on the build machine: a core linked to one libTorch, loaded into a Python process that had another, used to break import torch.

libTorch is the C++ library, found like any C++ dependency: Torch_DIR when given, else the conda environment's libtorch package ($CONDA_PREFIX/share/cmake/Torch), else wherever CMake finds one. Only its own three libraries are linked, by path. Nothing here needs Python's torch package, so a conda package of libKalmanLearn depends on libtorch alone.

A process holds one libTorch. Where Python's torch is imported in the same process (training a router, say), it must be the same installation; conda's libtorch and pytorch are.

The field solver on libTorch

Kalman::Learn::Solvers::Vorticity steps many 2-D vorticity fields in one call: dw/dt = -u.grad(w) - beta v + nu lap(w) + F, pseudo-spectral, with any explicit Runge-Kutta tableau, on cpu, cuda or mps (single precision on mps, which has no double). It is what SpectralSolver(backend="torch") runs in Python: NS2D (Kolmogorov flow) and BetaPlaneNS2D state their terms (_vorticity_terms) and the steps happen in C++. Python's torch is not imported; there is no Python-Torch implementation of the solver any more. A solver with other physics uses backend="numpy".

The decision layer

Training in Python, deciding in C++

Routers::Neural is the seam between the two implementations, and it keeps the division of labour that routers/neural.py states in its opening lines:

  • the router owns feature extraction and normalisation — the NIS window, the front-padding, the standardisation;
  • the model owns the architecture and the forward pass.

So Routers::Neural holds a NN::Model and contains no inference runtime at all. That is what makes the runtimes genuinely optional rather than nominally so:

Backend Executes Needs When
NN::MLP a tanh MLP from its weights nothing the architecture is the MLP; you want zero dependencies
NN::Torch a TorchScript module libTorch highest fidelity — the same torch.nn module, traced
NN::Onnx an ONNX graph ONNX Runtime deployment — a 10 MB runtime, not tied to a Torch version

Python owns training; C++ owns inference; a trained policy is what crosses, not a language binding — once at load time, rather than once per step.

Both exports produce the same probabilities as the Python router; measured agreement is 2e-13 for ONNX and 1.8e-13 for TorchScript. Neither runtime is required: with neither present the routing layer still works through NN::MLP, and a Routers::Neural with no model falls back to the Bayesian update rather than failing.

The export bakes the feature standardisation and the softmax head into the graph, so a raw NIS window maps straight to probabilities and there is no second file to keep in step — a normalisation shipped apart from its weights still produces a valid-looking probability vector, which is the worst kind of bug. tests/test_router_export.py pins the equivalence; measured agreement between the Python router and the C++ one is 2e-13.

Two things that bite:

  • The IR version. Torch emits the newest ONNX IR it knows, and deployed runtimes reject it — ONNX Runtime 1.16 refuses anything above 9 with *"Unsupported model IR version: 10"*. export_onnx(..., ir_version=9) is the default for that reason.
  • The window must match. A policy trained at window=5 fed a window=7 history is a shape error, and Routers::Neural raises rather than guessing.

The rule for both optional backends: constructing one asks for a specific artifact, so a missing file or a missing runtime throws. The graceful degradation lives one level up, in Routers::Neural, which routes by Bayes when it has no usable model. A missing optional dependency costs you the policy, never the filter.

The factory: how a C++ model reaches Python

libKalman ships no physics, so the question is how physics written against it — in an application, a ROOT+ analysis, a plugin — becomes visible to something that did not compile it. The answer is one line per model:

class ConstantVelocity : public Kalman::Models::Linear { /* F, H, Q, R ... */ };
KALMAN_REGISTER_MODEL(ConstantVelocity, "constant-velocity");
KALMAN_REGISTER_MODEL(ConstantVelocity, "constant-velocity-slow", 10., 0.5, 0.2); // configured

The registrar runs at static-initialisation time and Kalman::Factory::Instance() then knows the name: Names(), Has(), Describe() (title, dimensions, engine, origin) and Create() — a fresh std::unique_ptr<Model> with no knowledge of the type. Names are lowercase-hyphenated by convention so they can never be mistaken for the CamelCase Python classes they sit beside. Every failure is loud: a duplicate name, an unknown name, a library that registers nothing.

Plugins. A translation unit like examples/cxx/example_plugin.cc compiled as a shared library (libKalmanPlugin_example) is a plugin: Factory::LoadPlugin(path) dlopens it, the registrars run, and its models are in the catalogue. The plugin may link anything it likes — ROOT, RooFit, a detector library — because the framework only ever sees Kalman::Model. That is the one code path by which a model written for ROOT+ reaches the Python side, and ROOT stays inside the plugin.

The C API. Kalman/CAPI.h is the flat extern "C" view of the factory, of a model, and of the engines — kalman_factory_* to discover and load, kalman_model_* to construct one and evaluate F/H/B/L/Q/R, f/h, the Jacobians and the initial state, kalman_engine_* to build a C++ engine and run its predict / update / innovation / smooth steps, and kalman_filter_run for a whole Kalman::Filter pass (forward, optionally RTS) in one call. All row-major double arrays, 0/-1 returns and kalman_last_error(); no exception crosses it. tests/cxx/06_factory.cc covers the registry, the loader and the model surface.

The Python side. modules/framework/native/core.py dlopens the library through cffi in ABI mode (no compiler) and NativeModel in modules/framework/models/native.py wraps a factory instance as a KalmanModel:

from kalman.framework import NativeModel
import kalman.api as api
api.load_plugin("KalmanPlugin_example") # by name, from the allow-listed dirs
m = NativeModel("pendulum", "sensor-1") # a C++ model ...
rec = m.filter(m.sample(5.0).zk) # ... driven by the Python EKF
api.run_filter({"base": "constant-velocity", "sensor_id": "cv", "fs": 20}, zk)

Every registered name becomes a class in api.catalog()["models"], describe() reports "backend": "native" with its plugin, and the MCP list_models / run_filter / forecast tools need no change. fs=, x0=, P0= given from Python are pushed into the C++ instance, so both sides agree on every step.

The engines cross too, in the same direction. NativeEngine("extended") is a KalmanEngine whose predict / update / smooth run in C++ behind the ordinary Python KalmanFilter (records, diagnostics and plots unchanged), and NativeModel.filter_native(zk, engine=..., smooth=...) runs the whole Kalman::Filter pass fused in one call and hands back a KalmanRecord. In a spec, "bindings": {"engine": "extended", "backend": "native"} selects it. Both need a native model: there is no route from a C++ engine back into a Python-defined f, by design.

What crosses, and what does not. One C call per f, h or coefficient evaluation — cheap, and in the direction the measurements below say is affordable. What does not cross is a Python callback from inside a C++ loop; a Python-defined model keeps running on the Python engines, and a C++ model on either side. The library is found through KALMAN_LIBRARY, KALMAN_ROOT, or this checkout's var/install/lib; without it the Python package simply reports catalog()["native"]["library"] = None.

Loading a plugin runs code. So api.load_plugin takes a plugin name, not a path, resolved only inside allow-listed directories (KALMAN_PLUGIN_PATH, default: this checkout's var/install/lib and var/build/lib); a path is accepted only when it already lies inside one of them, after realpath. It is gated by its own scope, load_plugins — never by write_models, which only ever writes data — and the MCP tool of the same name exposes exactly that.

Load once, known everywhere. load_plugin also records the plugin name in the shared registry (see REST API). The REST server, the MCP server and every other process on the same state directory load it again by name, from their own allow-listed directories. This also occurs after a restart. Subscribers get a plugin.loaded event that lists the new models. Thus a model written in C++ (in a ROOT+ analysis, for example) is published with one call, POST /plugins {"name": "KalmanPlugin_mine"}, and Unity, agents and other users can then use it as a spec base.

A model written in Python that is nothing but its matrices needs no twin written for it: the framework builds the C++ model itself (Kalman::Models::Tabulated) and runs the whole pass on it.

Model files: <tt>.kw</tt>

A model can be written to one file and read back, by the same code for every model (Kalman::IO::ModelFile, through the Kalman::Model interface; nothing is written per model).

kalman export constant-velocity -o cv.kw # a model of matrices: written whole

kalman export ballistic --linearize -o tangent.json
kalman export car-speed --set mass=1200 # model.json on the standard output
kalman model cv.kw # what a file holds

What a file can hold

Code cannot be put in a file, so what is written depends on what the model is made of. A model says so with SetStructure(); Models::Linear declares Matrices, Models::Extended Maps, and a model that says nothing is Maps, so it is never written out as if its matrices were all of it.

Model::Structure() The file (kind) Reads back
Matrices: constant F, H, B, L, Q, R complete: all of it (A and Qc instead of F and Q when stated in continuous time) anywhere, with no plugin
TimeVarying: matrices that change with time complete over --steps N samples: the matrices that change, as tables anywhere, with no plugin
Maps: f and h are code reference: the registered name, its plugin, parameters, Q, R, x0, P0, fs where that plugin is installed
any, with --linearize linearization: the Jacobians at the initial state, as a Matrices model anywhere; valid near that state only

A linear model that overrides F(t), H(t), Q(t) or R(t) with something that depends on t declares SetStructure(StructureKind::TimeVarying); one that overrides f() or h() declares Maps.

The format

A .kw file ("Kalman World") is one zip archive, so the parts of a model cannot be separated or mixed with another model's, and any zip tool opens it:

Entry Holds
model.json the readable part: format ("kalman-model"), format_version, kind, origin (name, plugin, title), structure, dynamics, the state and measurement components with their units, and spec
tables/<F,H,Q,R>.f64 one matrix per sample for a matrix that changes with time: raw little-endian float64, row-major, of the shape [steps, rows, columns] given in model.json

spec is exactly what the JSON API takes (kalman.api.make_model, the REST and MCP servers): base, fs, dynamics, noise, initial, labels, bindings. Numbers are written so that a double reads back unchanged.

model.json is always stored as it is, so the readable part stays readable. The tables are compressed with zlib when the library is built with it (KALMAN_USE_ZLIB, on by default; found on the system, optional) and stored otherwise. A build without zlib reads stored tables only and says so when it meets a compressed one. Every entry carries a CRC-32, checked on reading.

A file with no table may also be written as plain JSON, to a name ending in .json (the model.json alone). A file with tables is refused that way, since its JSON would not be the whole model, and a model.json whose tables are missing is refused on reading.

.kw is meant as the one container of Kalman World: format in model.json says what a file holds, so other kinds (records, controllers) can use the same archive later without a new extension.

  • A reference to a Python class carries the arguments it was constructed with, defaults included: every model records them when it is built (model._init_arguments). How a twin stays the same model. Nothing is defined twice:

  • The twin's scalars are the named parameters of Kalman::Model (DeclareParameter, SetParameter, ParametersChanged), pushed from the Python instance by name: omega, beta_drift, c_drag and so on.
  • The sample rate, Q and R are pushed from the Python instance on every run, and the initial state by the filter. A change made to the Python model after construction therefore reaches the twin.
  • Apps::Model differences f and h the way helpers.numerical_jacobian does (forward, step 1e-6 max(1, |x_j|)), not with the library's central scheme, so the two sides linearise alike.
  • A subclass or an instance that redefines f, h, F, H, B, L, Q or R is a different model from the one that was ported, and keeps the Python loop. For a continuous model derivative, after_step and substeps count too (the class's f is kept as derivative), and a model adds the helpers its dynamics call (guidance, clip_u ...) to its _TWIN_CONTRACT. So does any engine other than the plain extended one.

kalman.framework.models.native.USE_NATIVE_TWINS = False, or KALMAN_NATIVE_TWINS=0 in the environment, switches every twin off. That is how the "Python" column above is measured.

Field models on the ensemble engine

KolmogorovFlowModel and BarotropicFlowModel are fields: the state is the vorticity on a periodic grid (n = 4096 at 64 x 64), filtered by the ensemble engine through the hooks forecast, observe, localization and initial_ensemble. Their twins (Apps::Weather::KolmogorovFlow, kolmogorov-flow, and Apps::Weather::BarotropicFlow, barotropic-flow) implement Engines::EnsembleModel beside Kalman::Model: the members are forecast in parallel (one thread each, up to the threads parameter, 0 for every core), observed together, tapered with Gaspari-Cohn from the torus distances, and Q is read as its diagonal, so a cycle forms nothing of size n x n. With the ensemble engine model.filter runs Kalman::Filter over the twin, and TwinExperiment.run runs each method in one call of Filters::EnKF::Cycle, which keeps the means and the spread and no covariance.

Composite models: matrices, no twin

A CompositeKalmanModel stacks its parts: block-diagonal F and Q, and an H that stacks the parts' readouts (INDEPENDENT) or sums them on one shared channel (FUSED). The oscillator windows (OscillatorModel and its harmonic and inharmonic ladders), OscillatorBankModel and InterferometerModel with its detectors K1, H1, L1 and V1 are composites of AnalyticOscillatorModels, each of them constant matrices. They need no twin: a composite reads its structure from its parts (MATRICES when all are constant matrices, TIME_VARYING when one of their matrices is a function of time, MAPS as soon as one part is code or a stacked map was replaced after construction), and an instance that is not code takes the linear engine (DEFAULT_ENGINE read on the class stays the extended engine, which serves any part). filter() then runs kf_forward_linear and the smoother kf_backward_rts on the stacked matrices, and sample() runs its state chain in C++ (kalman_propagate on a Models::Tabulated holding them, numpy's draws). A time-varying composite stores the stacked matrix that changes as a function of time (_F, _H, _Q, _R), as any model built from one does, so the pass over tables and the exporter tabulate it; it never takes the constant-matrix pass.

Before, these models ran on the extended engine: the C++ loop calling the Python closures for f, F, h, H, Q and R at every step, and the smoother in Python. ROOT::IOPlus::TKalmanRecord takes a Kalman::IO::Record and adds the two things libKalman deliberately does not provide: a TObject with a ClassDef so a result goes into a TFile, and TGraph / TGraphErrors / TMultiGraph of the estimate with its band. Point CMake at a prefix with -DKalmanFramework_ROOT=<prefix>. The class stays ROOT::IOPlus::TKalmanRecord, not a Kalman:: sub-namespace: root-plus' namespace is flat, and a nested Kalman would shadow the framework's own Kalman:: in every lookup.

‍Not ROOT::IOPlus::TKalmanFilter. That is root-plus' own small self-contained linear filter, now its neighbour in the same directory and unrelated to this framework. A ROOT+ model — physics that wants TF1 or RooFit inside f() — does not go here either. It is a plugin (previous section): it links ROOT, registers with Kalman::Factory, and the Python side loads it by name.

Where the Python boundary is, and why

Every model of the catalogue filters, smooths and samples in C++ (tests/test_native_matrices.py::TestNoModelFallsBackToThePythonLoop fails when one does not). Which pass a model takes:

The model is The pass
given by code, with a twin in libKalmanApps the twin, on the extended, unscented or particle engine; the ensemble engine for the field models; the combinatorial one for the drift chamber
its matrices, constant the linear kernel, or Tabulated on the extended engine
its matrices, functions of time (calorimeter, power grid, phasor) Tabulated with tables
a composite of such models (oscillators, the interferometer) as its parts: matrices
C++ already (NativeModel, a .kw file) itself
written in Python with its own f and h and no twin (a user's model, examples/python/toy_model.py) the C++ loop, calling back into f and h at each step

What still runs in Python, and why:

  • A model written in Python by a user. That is the point of the last row: nothing to compile, at the cost below. Writing it in C++ (the toy shows both) or giving it a twin removes the cost.
  • Code handed in as an argument: a steering flow or an intensity function for the storm, a controller function in the loop, a custom integrator, a surrogate forecast for the flow. A Python callable cannot run in C++; the model then keeps its Python physics, or the C++ loop calls back.
  • The interferometer with its violin-bank controller (a controller on a model that takes no control input): the Python loop.
  • The libTorch backend of the field models inside the assimilation loop (libKalmanApps does not link libKalmanLearn); the solver itself is C++.
  • Around the filter: preprocess and postprocess (demodulation, the relativistic corrections), event and hit generators that draw with numpy's generator, spectra and peak fits, plots, the servers.
  • Random draws are made by numpy and handed to C++, on purpose: a seeded run gives the same numbers on either side.

The cost of the callback row, measured on BallisticModel before it had a twin:

model.f (Python/numpy/scipy) : 20.74 µs per call
whole native predict + crossing : 3.75 µs per call

One callback costs ~6× the entire native step it would sit inside, and an EKF needs ~21 of them per step for the Jacobian. Profiling agrees: of 5.74 s for a 6000-step EKF, 88% is numerical_jacobian + model.f. Amdahl caps the win at ~1.1× even if the covariance algebra became free.

That is exactly why the Python package's native path (modules/framework/native/) engages only where it can eliminate callbacks entirely — the arithmetic of a step once the model has been evaluated, and, for constant matrices with no control callable, all N steps fused into one call. The limit is the language boundary, not the language.

Those kernels are now this library's own kf_* / ukf_* / pf_* / diag_* entry points (src/Kernels.cc): a fused linear pass is a Kalman::Filter over Engines::Linear, an update is Utils::Correct, so a Python model here and a C++ model in ROOT+ run one implementation. The Python package used to carry a hand-rolled C copy of the same arithmetic on stack arrays, which was faster — 21× on the linear forward pass against numpy, where the C++ classes with their heap-allocated Matrix/Vector temporaries measure 2.4× (2.6× geometric mean over the kernels, tests/bench_native.py). One implementation was chosen over the second copy; the speed is recoverable inside the C++ types (small-buffer storage for the n ≤ 16 case) without touching either side of the seam, and that is the next performance step, not a design limit.

So the seam sits where a crossing is paid once per evaluation into C++ — a compiled model evaluated by a Python engine — and never once per step out of it. The portable artifacts between the two sides are a registered model (through the factory), data (a record) and a trained ONNX policy.
